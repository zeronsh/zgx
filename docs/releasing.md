# Releasing

zgx 0.2.0 is on crates.io (published 2026-11-25 to 27, tag `v0.2.0`; 0.1.0, the first, on 2026-10-25). This is how a release goes, and what it checks.

## Version scheme

- Every published crate shares one version, the workspace's (`[workspace.package] version` in `Cargo.toml`). Path dependencies between them name it (`version = "0.1.2"`), as crates.io needs.
- It follows [semver](https://semver.org) as Cargo reads it before 1.0: `0.MINOR.PATCH`, where a new minor may break apps (each break listed in `CHANGELOG.md` with what to check and how to migrate) and a patch does not.
- A release is a tag `v<version>` on `main` (`v0.2.0`), made once its changelog section is written: `scripts/changelog.py assemble --version 0.2.0 --date <date>` puts `changelog.d/`'s entries into `CHANGELOG.md`'s "Unreleased", which becomes `## 0.2.0 (date)`, and deletes them (`release_check.sh` fails a release commit that leaves any). A breaking release gathers what apps must change in a "Migrating from <previous>" block at the section's top, its entries moved there by hand in the release commit, each once and none lost.
- A fix to a release already out (a patch with nothing else in it) branches from that release's tag, not from `main`, whose later changes would each need their semver check and dry run: `release-0.1.2` is `v0.1.1` and the fix, tagged `v0.1.2` on that branch and published from it, the fix then brought to `main` by its own pull request (as 0.1.2 was).
- The oldest Rust the workspace builds with is `rust-version` (1.95: `AtomicU64::try_update`). CI's Linux job checks it: its no-default-features check runs on that toolchain.

## Vendored data

zgx carries ICU4X's Thai word dictionary for its `cjk-thai-words` feature (`crates/zgx/data/thaidict.bin`, 131,759 bytes). ICU4X's compiled data keeps Thai in one table with Burmese, Khmer and Lao, and linking it would add the other three (about 0.9 MB). Chinese and Japanese come from that compiled data as a dependency. The file is extracted from `icu_segmenter_data` 2.4, the version zgx's `icu_segmenter = "~2.4"` pins, by `scripts/extract_thai_dictionary.py`. It reads the locked crate from Cargo's registry, writes the same bytes from the same source, and with `--check` (the release check runs it) fails if the committed file differs.

- **Licence.** The data is Unicode's, under the Unicode License v3, a permissive one. So zgx's `license` is `MIT AND Unicode-3.0`, and its package ships the licence text as `data/LICENSE-UNICODE` (the release check fails without it). A release's metadata and semver check expect that field, which changed after 0.1.3.
- **Moving ICU4X on** (2.5, say):
  1. Bump `icu_segmenter`, `icu_provider` and `icu_collections` in `crates/zgx/Cargo.toml`, and `PINNED` in the script, together.
  2. Run `cargo update -p icu_segmenter`.
  3. Run the script, and copy that version's `LICENSE` from `icu_segmenter_data` over `data/LICENSE-UNICODE`.
  4. Run zgx's `words::` tests. They read Chinese, Japanese and Thai words, so they catch a dictionary that didn't load.

  If the data's layout changed (2.4 moved Thai from a char16 trie to an alphabet and a `ZeroTrieSimpleAscii`), the script stops and says so. Then the script and `words.rs`'s provider change with it.

## What stays patched in the repository alone

The workspace's `[patch.crates-io]` keeps the rest: wgpu-hal (Metal command buffers made lazily and never empty, a Direct3D 12 adapter exposed without opening the others), winit (a Wayland window's `xdg_surface`, X11's `_NET_WM_SYNC_REQUEST` and `_NET_WM_USER_TIME`), and AccessKit's consumer and adapters for macOS, Windows and Linux (headings, grid rows, tables, tree items, a field's error message). Forking them would mean forking what depends on them too (wgpu, accesskit_winit). An app depending on zgx from crates.io gets their releases instead, and zgx builds and runs with them, without those fixes:

- **winit**: Wayland popups open in their window, as on a compositor without `xdg_popup`, instead of as popup surfaces of their own. Text dragged in from other apps drops into fields on Wayland alone (zgx's own data device takes it; on macOS, Windows and X11 the platform's drag reaches winit's windows, whose hook is the patch's), and macOS's Services don't act on zgx's selected text. A Wayland input method isn't told a field's input mode (email, URL, number, phone): every field is plain text to it. On macOS a key a web page or terminal has the keyboard for is never the app's: neither its reserved shortcuts nor one the page leaves alone. Glass blurs on KWin alone (`org_kde_kwin_blur`): Hyprland and other compositors with `ext-background-effect-v1` aren't asked. On Windows a covered window goes on drawing (no `WindowEvent::Occluded`), `set_theme` doesn't change what `theme()` answers and a system change undoes it (the window's Mica goes back to the system's; its caption buttons stay in the app's ink), a window switched light or dark in Settings can keep the mode it had, each user event costs a posted message and a second message round, and over a window behind another Shift and Control read as up (Shift with the wheel scrolls down there, not across). Files dragged in carry no position on macOS, Windows or X11, so they hover and drop where the pointer last was. macOS's trackpad swipe between pages doesn't navigate. On X11 a window hears raw pointer moves anywhere on the screen until it has had focus and lost it, an input method's server that has gone or hangs can hold a window's close, and a wheel notch from a pointer with no scroll valuators scrolls two lines and zooms two levels. The X11 changes are behaviour alone: a window manager's resize no longer waits for frames, and focus-stealing prevention sees no user time.
- **wgpu-hal**: Metal frames take upstream's command buffers (more per submission), its fence waits (polled each millisecond) and its blit encoders for buffer fills and copies (`vendor/wgpu-hal/ZGX_PATCH.md` measured 297 MB of graphics memory at a small window's launch with them, 185 without). A window at rest keeps Metal's queue and its memory, and an app shader's pipeline keeps its shader's whole IR. On Windows, `request_adapter` ranks the adapters, opening a device on each, and shaders compile at each launch (no cache between launches). wgpu devices an app makes of its own on WARP submit at once, which faulted in `d3d10warp.dll` in that file's test (zgx's renderers share one device there). On Linux every present copies the whole frame into its swap chain image (with the patch, only what that image lacks: wgpu's own barrier lets the image's pixels go, so a partial copy would show lost ones) and names no changed regions to the compositor, so a small change in a large window costs a whole copy.
- **AccessKit**: VoiceOver's rotor misses headings and its table navigation finds no grid rows; Narrator and Orca lose what their patches add. An invalid field's error is said in its description rather than as the platform's own invalid flag and error message (zgx-desktop sees which it has by the vendored consumer's `links` metadata, so patch the consumer with the adapters, never alone). Everything else reads as before.

Where a patch adds an API zgx calls (winit's `xdg_surface`, `text_drop` and `SelectionServices`, wgpu-hal's `expose_preferred_adapter`, `Queue::renew` and `zgx_single_use_next_module`), zgx detects it at build time: the vendored crate carries `links` metadata (`links = "zgx_winit"`, `"zgx_wgpu_hal"`) whose `patched` key reaches the build scripts of the crates depending on it (zgx-desktop, zgx-gpu), which set `zgx_winit_patched` and `zgx_wgpu_hal_patched`. With crates.io's crates neither is set, and the fallback above is compiled. Nothing to enable: a build in the repository has every patch, any other has none. `scripts/unpatched_check.sh`, in CI's Linux and macOS jobs, checks the crates in a copy without `[patch.crates-io]`: a patched function called outside its cfg fails there, where the repository's own builds have it. (`zgx-gpu` did from November 9 until it was added.)

## Follow-ups: patches to drop

- **harfrust**: from 0.9 a shaper takes font functions of its own (`FontFuncs`, `ShapeOptions::font_funcs`), which could keep a variable instance's advances from cosmic-text. Upgrading cosmic-text's harfrust to it (0.5 → 0.9 changes its API) and keeping them there drops `zgx-harfrust`.
- **taffy**: the auto-margin gaps fix shipped upstream in taffy 0.14.0. Upgrading zgx's layout to it (0.9 → 0.14 changes taffy's API) drops `zgx-taffy` for crates.io's taffy.
- **alacritty_terminal**: dropped once a release of it stops implementing comparisons on `usize` and `i32` (upstream isn't asked: zgx keeps its forks).
- **vte**: kept with `zgx-alacritty-terminal`, which writes the runs it prints (`Handler::input_str`).
- **winit**: native popups are on winit's master (the 0.31 betas). Upgrading to 0.31 drops the `xdg_surface` accessors (Wayland popups through winit's own), and with them `zgx_winit_patched`; the X11 changes are to check against it then.

## What a release checks

`.github/workflows/release.yml` runs on a `v*` tag, or by hand (Actions → Release dry run), on Linux, macOS and Windows (each has fallbacks of its own to build). It checks that the tag is the workspace's version, then runs `scripts/release_check.sh`:

1. Each fork is packaged and built from its package, against crates.io.
2. Every published workspace crate is packaged and built from its package, in dependency order (`cargo publish --workspace --dry-run`). That build leaves the workspace's `[patch.crates-io]` out: winit, wgpu-hal and AccessKit come from crates.io, as an app depending on zgx gets them, so what only builds with a vendored patch fails it. The forks, which crates.io has only once the release publishes them, are given from `vendor/` (`--config 'patch.crates-io.zgx-cosmic-text.path="vendor/cosmic-text"'`) for that run alone.
3. A new app with no lockfile depends on what 1 and 2 packaged, every other crate resolved afresh from crates.io as `cargo add` resolves it, and runs a Luau script headless. zgx's lockfile holds its dependencies where they were tested; a new app's does not, and a new release of one (luau0-src 0.22.1, Luau 744) failed every Luau app at start while 1 and 2 passed.
   Another app turns on every feature each published crate has on this platform, built from those packages too: 2 builds default features alone, and a feature's files left out of a package, or code only it compiles (Ghostty's terminals, WebView2), would otherwise first fail for an app turning it on. A feature for some platforms alone says which in the script's table; any other is built everywhere. Ghostty is fetched and built with Zig 0.16 into a cache of the check's own, as a user's first build is: a Mac running the check needs Zig 0.16 (`release.yml` installs it there; Windows and Linux terminals are zgx-terminal's, with no Zig). The app only names each crate, so a native library has to exist to link, not resolve every symbol: the examples' builds do that.
4. Each published crate's previous release, from crates.io, builds against every other zgx crate 2 packaged, as an app on it gets them from `cargo update`. It calls them where a change semver-checks passes over still breaks it: a return type (0.1.3's `PaintItem::matrix`, put back before it shipped), a `doc(hidden)` function (`zoom::wheel`, put back for 0.1.4), or a struct it builds field by field (zgx-script 0.1.6's `TabsOptions`, given `..Default::default()` before 0.1.7 shipped). A crate new in the release has none. At a breaking version (0.1.x to 0.2.0) those crates ask for versions Cargo won't give them from this release, so it says it isn't checked and runs `scripts/previous_scripts.py` in its place: the previous release's templates, written by its own `zgx`, and its examples, each under both `zgx test`s.
5. `cargo semver-checks` of each against its previous release, and `scripts/semver_verdict.py` over what it finds: every failure it reports fails the check unless the release accepted it. Two things accept one. A new pub field on a struct with `Default` (derived or implemented) is taken, as an app's literal can end with `..Default::default()`, given its migrate note; on a struct without it the app has no way to keep compiling (zgx-script's `driver::Line` and `Window` at 0.1.7's first freeze, which kept their 0.1.6 fields in #1272), and a struct the script can't find (one a macro writes) fails, to check by hand. Anything else (a type no longer `Send`, as zgx-gpu's `TextCache` at 0.1.8's pre-flight; a removed item; a changed signature; a variant on an exhaustive enum) needs a line in `scripts/semver_allowed.txt`, `release | crate | lint | item | reason`, counting for that release alone: the ruling and its reason reviewed in a PR like any change, and the changelog's migrate note beside it. `release.yml` installs cargo-semver-checks; a machine running the check needs it (`cargo install cargo-semver-checks --locked`).

It never publishes. It doesn't run on pull requests: CI's time is unchanged. Locally, `scripts/release_check.sh --allow-dirty` checks uncommitted work. In Git Bash on Windows, coreutils' `link` comes before MSVC's on the path, and every build script fails to link ("link: extra operand"): set `CARGO_TARGET_X86_64_PC_WINDOWS_MSVC_LINKER` to MSVC's `link.exe` (GitHub's runners don't need it). Before a release, the check can run on machines of our own while CI's queue is long: 0.1.3's ran in the Linux container and on a Windows PC as well as macOS.

## Publishing

Not automated, on purpose: publishing needs a crates.io token, and is done by hand, in this order, each after the release check passes on the release commit (on its branch, `Release dry run` by hand; the tag comes after publishing, below):

1. The forks that changed since they were last published, their versions bumped, `zgx-harfrust` and `zgx-swash` before `zgx-cosmic-text` (which depends on them): `cargo publish --manifest-path vendor/harfrust/Cargo.toml`, `vendor/swash`, `vendor/cosmic-text`, `vendor/taffy`, `vendor/mlua --features luau`, `vendor/zune-jpeg`, `vendor/vte`, `vendor/alacritty-terminal` (which depends on `zgx-vte`), `vendor/arboard`.
2. The workspace: `cargo publish --workspace --locked` (it orders the crates itself). With more than five names new to crates.io, one crate at a time instead: see [new names](#new-names).

`cargo publish --workspace` can stop part way with cargo's own error "no packages ready to publish but … remain in plan … awaiting confirmation" (cargo 1.96, at 0.1.0 and again at 0.1.2, each time after `zgx-gpu`; 0.1.1 went through): what it uploaded is published (check crates.io), and the rest publish one at a time in dependency order, each once the one before is in the index (`curl https://index.crates.io/zg/x-/zgx-gpu`): `cargo publish -p zgx-script --locked`, then `zgx-terminal` (before the desktop host, which depends on it), then `zgx-desktop`, then `zgx-run`.

crates.io's index can stop taking new versions for everyone while uploads still succeed (2026-10-26, about four hours from 04:46 UTC; its status page said operational): the API lists the version, the index (`https://index.crates.io/zg/x-/<crate>?cb=<anything>`, past its cache) answers 404, and nothing depending on it publishes. Check that other crates' newest versions are missing too before blaming ours; a version bump doesn't help (zgx-harfrust 0.5.2 and 0.5.3 both waited). Wait, and go on once it answers.

Once every crate is in the index, and the new project below builds from crates.io and runs, tag the commit (`v<version>`), make a GitHub release from its changelog section's head (the summary, highlights and migrating notes; the whole section can be too long for one) with a link to `CHANGELOG.md` at the tag (its links absolute, `https://github.com/zeronsh/zgx/blob/v<version>/…`: a release resolves no relative ones), and check a new project, with no lockfile, builds from crates.io alone and runs: `cargo add zgx zgx-desktop zgx-script zgx-run`, a `main` calling `zgx_run::run` on an `app.luau`, launched to its window. Building is not enough: 0.1.0 and 0.1.1 built in a new project and panicked as their first script loaded (luau0-src 0.22.1, resolved afresh; the release check's third step now runs one).

A crate on crates.io can't be deleted, only yanked: a version published is published for good.

### New names

crates.io limits how fast one account publishes, new names apart from new versions: five new names at once, then one each 10 minutes; thirty new versions at once, then one a minute (the defaults in [crates.io's `rate_limiter.rs`](https://github.com/rust-lang/crates.io/blob/main/src/rate_limiter.rs), read 2026-11-24; an account can have limits of its own, so check it again). `cargo publish --workspace` orders crates by their dependencies, not by that limit, so a release with more than five new names publishes one crate at a time, each once the one before is in the index.

0.2.0 published seven (`zgx-swash`, `zgx-vte`, `zgx-arboard`, `zgx-audio`, `zgx-module-macros`, `zgx-module`, `zgx-text`), one crate at a time in dependency order (the forks, then `zgx`, `zgx-audio`, `zgx-module-macros`, `zgx-module`, `zgx-text`, `zgx-gpu`, `zgx-components`, `zgx-3d`, `zgx-ghostty-sys`, `zgx-script`, `zgx-terminal`, `zgx-desktop`, `zgx-run`), with no refusal: the first new name went up over an hour before the sixth. `zgx-fx` and `zgx-video` are held (`publish = false`), as no published crate needs them: their docs and `zgx video`'s error say "from the repository". A new workspace crate is published unless it says `publish = false`: decide for each before a release (`zgx-ladybird-sys`, new after 0.2.0, says it).
